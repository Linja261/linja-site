Kontext, Harness, Loop. Drei Ebenen, die Produktteams gerade durcheinanderbringen.

TL;DR

Context, Harness und Loop Engineering sind keine Synonyme, sondern drei aufeinander aufbauende Ebenen: Kontext legt fest, was ein Modell für einen einzelnen Aufruf sieht, das Harness legt die Umgebung eines Agenten fest, der Loop legt fest, wer ihn anstößt. Jede Ebene erbt die Schwächen der darunterliegenden. Alle drei enthalten Entscheidungen, die auf den Produkttisch gehören und nicht in die Implementierung.

In Produktteams wird über Modelle diskutiert, obwohl das Modell selten der Engpass ist. Seit Anfang 2026 hat sich dafür eine Formel durchgesetzt: Agent = Modell + Harness. Innerhalb weniger Monate sind daraus drei Begriffe geworden, die nebeneinander benutzt werden, obwohl sie verschiedene Ebenen meinen. Wer sie nicht trennt, behandelt einen falschen Agentenlauf als Prompt-Problem statt als Systemfehler und kauft im Zweifel Beratung für die oberste Ebene ein, während das Problem ganz unten sitzt. Die Sortierung ist deshalb keine Begriffsklauberei, sondern die Voraussetzung dafür, den richtigen Hebel zu finden.

Drei Ebenen, die ständig verwechselt werden

Context Engineering ist die unterste Ebene. Anthropics Applied-AI-Team definiert sie als die Menge an Strategien, mit denen während der Inferenz die optimale Auswahl an Token kuratiert und gepflegt wird.1 Der Unterschied zum Prompt Engineering liegt darin, dass diese Kuratierung nicht einmal stattfindet, sondern vor jedem einzelnen Aufruf neu. Die Regel dazu ist ein Weglass-Auftrag: die kleinstmögliche Menge hochwertiger Token finden, die das gewünschte Ergebnis wahrscheinlich macht.

Harness Engineering sitzt darüber und beschreibt die Umgebung, in der ein einzelner Agent handelt: Systemprompt, Werkzeuge, Skills, MCP-Anbindungen, Sandbox, Rechte, Hooks, Dateigedächtnis und die Prüfungen, an denen ein Ergebnis scheitern kann.

Loop Engineering sitzt noch eine Ebene höher und beschreibt das System, das einen Agenten wiederholt anstößt, Helfer startet, Ergebnisse verifiziert und den Zustand weiterträgt, ohne dass ein Mensch Zug um Zug promptet. Addy Osmani hat den Begriff am 7. Juni 2026 geprägt, ausgelöst von Boris Chernys Satz „I don't prompt Claude anymore. I have loops running that prompt Claude and figuring out what to do. My job is to write loops".2

Die Reihenfolge ist keine Geschmacksfrage. Jede Ebene erbt die Schwächen der darunterliegenden und ein Loop, der ein lückenhaftes Harness immer wieder aufruft, macht den Fehler nicht kleiner, sondern nur schneller.

Ebene Legt fest Symptom, wenn hier das Problem sitzt
Context Was in einem einzelnen Aufruf steht: ausgewählte Dokumente, Beispiele, Regeln, Verlauf Der Agent liefert schon bei einer einzelnen Aufgabe unzuverlässig
Harness Die Umgebung eines Agenten: Werkzeuge, Rechte, Sandbox, Gedächtnis, Prüfungen Der Agent liefert, verfehlt aber die Standards und bemerkt eigene Fehler nicht
Loop Wer den Agenten anstößt, wie oft, mit welchem Budget und welcher Abbruchbedingung Jeder Durchlauf braucht einen Menschen, der ihn von Hand startet

Woher der Begriff Harness kommt

Mitchell Hashimoto beschrieb am 5. Februar 2026 sechs Stufen seiner eigenen KI-Nutzung.3 Auf Stufe fünf steht die Gewohnheit, für die er den Namen prägte: „I've grown to calling this 'harness engineering'". Die Regel dahinter passt in eine Zeile. Sobald ein Agent einen Fehler macht, investiert man die Zeit, eine Lösung zu bauen, damit er genau diesen Fehler nie wieder macht.

Wenige Wochen später beschrieb Ryan Lopopolo für OpenAI ein Projekt nach dieser Logik, nach eigener Darstellung fünf Monate, rund eine Million Zeilen Code und etwa 1.500 gemergte Pull Requests von drei Engineers, ohne von Hand getippten Code.4 Die Menschen schrieben dort nicht den Code, sondern die Umgebung, in der Code entstehen konnte.

Anthropic hat im März 2026 einen Aspekt nachgeschoben, der in der Begeisterung leicht untergeht. Jede Komponente eines Harness kodiert eine Annahme darüber, was das Modell nicht allein kann, und diese Annahmen gehören regelmäßig auf den Prüfstand.5 Mit jedem neuen Modell kann ein Stück Gerüst überflüssig werden, das vorher nötig war.

Wie so ein Gerüst konkret aussieht, zeigt ein früherer Beitrag von Justin Young.6 Er beschreibt drei wiederkehrende Fehlermuster von Agenten, die über mehrere Sitzungen arbeiten: Sie versuchen alles auf einmal, sie erklären ein Projekt für fertig, weil sie irgendeinen Fortschritt sehen, und sie markieren Funktionen als erledigt, ohne sie wirklich getestet zu haben. Die Gegenmittel sind unspektakulär und genau deshalb lehrreich: eine Anforderungsliste als JSON, an der der Agent nur ein Statusfeld umstellen darf, eine Fortschrittsdatei, saubere Commits und ein Startskript. Selbst das Dateiformat ist bewusst gewählt, weil das Modell JSON seltener eigenmächtig überschreibt als Markdown.

Warum das Produktentscheidungen sind

Die Bestandteile klingen technisch, die Entscheidungen darin sind es nicht.

Auf der Kontextebene ist ein endliches Aufmerksamkeitsbudget zu verteilen. Jedes Token verbraucht Kapazität und die Genauigkeit sinkt messbar, je voller das Fenster wird.1 Zu entscheiden, was hineindarf und was draußen bleibt, ist Priorisierung unter Knappheit, also der Kern von Produktarbeit.

Auf der Harness-Ebene entscheidet der Zuschnitt der Werkzeuge über den Funktionsumfang. Ken Aizawa argumentiert, dass gute Agentenwerkzeuge nicht die vorhandene Schnittstelle spiegeln, sondern entlang der Arbeitsabläufe geschnitten werden, die ein Agent wirklich braucht.7 Benjamin Font Pera sortiert die Bausteine zusätzlich nach Wirkungsrichtung: Guides wirken vor der Generierung und geben Regeln, Spezifikationen und Vorlagen mit, Sensors wirken danach und prüfen das Ergebnis, damit der Agent sich selbst korrigieren kann.8 Diese Trennung lässt sich direkt in eine Spezifikation übernehmen, weil sie zwei Fragen erzwingt, die sonst untergehen: was der Agent vorher weiß und woran sein Ergebnis hinterher scheitert.

Auf der Loop-Ebene entscheidet die Abbruchbedingung. Ein Loop ohne erreichbares Ziel, ohne Budget und ohne Prüfung, die ihn beendet, ist kein autonomes System, sondern ein unbeaufsichtigter Kostenposten.

Kontext, Harness und Loop legen fest, was ein Agent sieht, was er darf und wie oft er es tut. Das sind drei Produktentscheidungen und keine drei Implementierungsdetails.

Kritische Einordnung

Das Vokabular ist Monate alt und noch nicht gesetzt. codecentric beschreibt offen, dass im eigenen Haus tagelang darüber gestritten wurde, was Loop Engineering überhaupt meint.8 Wer die Begriffe benutzt, beschreibt deshalb besser die Ebene, statt sich auf das Etikett zu verlassen.

Bei den Zahlen lohnt Zurückhaltung. Der OpenAI-Bericht ist die Erfahrungsbeschreibung eines Anbieters über sein eigenes Werkzeug, kein kontrollierter Vergleich, und die Anthropic-Beiträge stammen von der Firma, deren Modelle darin laufen. Belastbar bleibt vor allem der Befund von Harness-Bench, weil dort verschiedene Modelle und Harness-Konfigurationen unter gleichen Bedingungen gegeneinander antreten.

Der ernstere Einwand kommt von Osmani selbst. Er nennt drei Risiken: fehlende Verifikation („A loop running unattended is also a loop making mistakes unattended"), schleichenden Verständnisverlust und die Bequemlichkeit, zu den Ergebnissen keine eigene Meinung mehr zu haben.2 Dazu kommt die Gegenrichtung: Ein Harness kann Prüfungen so lange stapeln, bis von der Autonomie nichts übrig bleibt. Gartner sagt für Ende 2027 voraus, dass über 40 Prozent der agentischen KI-Projekte abgebrochen werden, unter anderem wegen steigender Kosten und unklaren Geschäftsnutzens.9 Wo die Grenze zwischen genug und zu viel verläuft, muss sich erst zeigen.

Was ich verändert habe und was noch fehlt

Mein persönliches Wissenssystem läuft seit Monaten auf den unteren beiden Ebenen, ohne dass ich Namen dafür hatte. Auf der Kontextebene eine Regeldatei im Wurzelverzeichnis und thematische Regelwerke, die nur bei Bedarf geladen werden. Auf der Harness-Ebene wiederverwendbare Kommandos als Werkzeuge und ein Pre-Commit-Hook als Sensor, der einen Commit blockiert, wenn versehentlich eine Datei mit Zugangsdaten darin liegt. Jedes dieser Teile ist als Reaktion auf einen konkreten Fehler entstanden, keines aus einem Konzept heraus. Es geht dabei um meine eigene Struktur wie Wochenplan, Artikelentwürfe und Lernziele, nicht um vertrauliche Firmendaten.

Die Bruchstelle sitzt an einer unerwarteten Stelle. Die Hooks liegen außerhalb der Versionierung. Auf einem neuen Rechner ist der Schutz weg und das Wissen darüber steht nur in einer Anleitung, die jemand lesen muss. Ein Sensor, den man von Hand wieder anschließen muss, ist kein Sensor.

Drei Dinge nehme ich mir vor. Die Hooks so ablegen, dass sie mitwandern statt in einer Anleitung zu überleben. Bei jedem Problem mit einer KI zuerst die Ebene bestimmen, statt sofort am Prompt zu drehen. Und für jede KI-Funktion, die ich künftig spezifiziere, Guides und Sensors getrennt aufschreiben. Ob das die Spezifikationen wirklich besser macht oder nur länger, wird sich in den nächsten Monaten zeigen.

Was bleibt für jeden Tag

Erst die Ebene bestimmen, dann den Hebel wählen

Unzuverlässig bei einer einzelnen Aufgabe heißt Kontext. Verfehlt die Standards heißt Harness. Braucht ständig einen Anstoß heißt Loop.

Guides und Sensors getrennt aufschreiben

Was der Agent vorher weiß und woran sein Ergebnis geprüft wird, sind zwei Fragen und gehören beide in die Spezifikation.

Jede Harness-Komponente ist eine Annahme

Sie sagt, was das Modell nicht allein kann. Mit dem nächsten Modell kann sie überflüssig werden, also regelmäßig prüfen.

Guides — Bausteine, die vor der Generierung wirken: Regeln, Spezifikationen, Vorlagen, Beispiele.

Sensors — Bausteine, die nach der Generierung prüfen und Rückmeldung zur Selbstkorrektur geben.

Agent — ein Sprachmodell, das über mehrere Schritte hinweg Werkzeuge benutzt und Zustand behält.

Systemprompt — die feste Anweisung, die vor jedem Gespräch gilt und Rolle sowie Regeln setzt.

Kontextfenster — die begrenzte Textmenge, die ein Modell pro Anfrage gleichzeitig verarbeiten kann.

Token — kleinste Texteinheit der Verarbeitung, grob ein Wortteil.

Inferenz — der Vorgang, bei dem ein trainiertes Modell aus einer Eingabe eine Ausgabe erzeugt.

Hook — automatischer Zwischenschritt, der bei einem Ereignis feste Regeln erzwingt.

Pre-Commit-Hook — Hook, der vor dem Speichern in die Versionsverwaltung prüft und notfalls abbricht.

MCP — offener Standard, über den Agenten an externe Werkzeuge und Datenquellen andocken.

Skill — festgehaltene Fähigkeitsbeschreibung, die ein Agent bei Bedarf nachlädt.

Sub-Agent — Helfer-Agent, der eine Teilaufgabe übernimmt und nur das Ergebnis zurückgibt.

Agentische KI — KI-Systeme, die eigenständig Handlungsschritte ausführen statt nur zu antworten.

Context, harness, loop. Three layers product teams keep confusing.

TL;DR

Context, harness and loop engineering are not synonyms but three layers stacked on each other: context settles what a model sees for a single call, the harness settles the environment an agent acts in, the loop settles who triggers it. Every layer inherits the weaknesses of the one below. All three hold decisions that belong on the product table rather than in the implementation.

Product teams argue about models even though the model is rarely the bottleneck. Since early 2026 one formula has taken hold: Agent = Model + Harness. Within months that turned into three terms used side by side although they name different layers. Teams that do not separate them treat a failed agent run as a prompt problem instead of a system fault, and end up buying help for the top layer while the problem sits at the bottom. Sorting the terms is therefore not pedantry. It is what makes the right lever findable.

Three layers that keep getting confused

Context engineering is the bottom layer. Anthropic's Applied AI team defines it as the set of strategies for curating and maintaining the optimal set of tokens during inference.1 What separates it from prompt engineering is that this curation does not happen once but before every single call. The rule attached to it is an instruction to leave things out: find the smallest possible set of high signal tokens that makes the desired outcome likely.

Harness engineering sits above it and covers the environment a single agent acts in: system prompt, tools, skills, MCP connections, sandbox, permissions, hooks, file based memory and the checks a result has to survive.

Loop engineering sits one floor higher and covers the system that triggers an agent repeatedly, spawns helpers, verifies results and carries state forward without a human prompting turn by turn. Addy Osmani coined the term on June 7, 2026, prompted by Boris Cherny's line: "I don't prompt Claude anymore. I have loops running that prompt Claude and figuring out what to do. My job is to write loops".2

The order is not a matter of taste. Every layer inherits the weaknesses of the one below it, and a loop that keeps calling an incomplete harness does not shrink the mistake. It only repeats it faster.

Layer Settles Symptom when the problem sits here
Context What goes into a single call: selected documents, examples, rules, history The agent is unreliable on a single task already
Harness The environment of an agent: tools, permissions, sandbox, memory, checks The agent delivers but misses your standards and does not catch its own mistakes
Loop Who triggers the agent, how often, on what budget and with what stop condition Every run needs a person to start it by hand

Where the term harness came from

Mitchell Hashimoto described six stages of his own AI adoption on February 5, 2026.3 Stage five holds the habit he named: "I've grown to calling this 'harness engineering'". The rule behind it fits in one line. As soon as an agent makes a mistake, you spend the time to engineer a fix so it never makes that specific mistake again.

Weeks later Ryan Lopopolo described a project at OpenAI built on that logic, by its own account five months, roughly a million lines of code and about 1,500 merged pull requests from three engineers, with no code typed by hand.4 The people there did not write the code. They wrote the environment the code could come from.

In March 2026 Anthropic added a point that tends to get lost in the enthusiasm. Every component of a harness encodes an assumption about what the model cannot do on its own, and those assumptions deserve regular stress testing.5 Each new model can render a piece of scaffolding unnecessary that used to be load bearing.

An earlier piece by Justin Young shows what such scaffolding looks like in practice.6 He describes three recurring failure patterns of agents working across multiple sessions: they try to do everything at once, they declare a project finished because they see some progress, and they mark features as done without really testing them. The remedies are unspectacular and instructive for exactly that reason: a requirements list in JSON where the agent may only flip a status field, a progress file, clean commits and a start script. Even the file format is a deliberate choice, because the model overwrites JSON less readily than Markdown.

Why these are product decisions

The components sound technical. The decisions inside them are not.

At the context layer a finite attention budget has to be allocated. Every token consumes capacity and accuracy measurably drops as the window fills.1 Deciding what gets in and what stays out is prioritisation under scarcity, which is the core of product work.

At the harness layer the shape of the tools decides the scope of the product. Ken Aizawa argues that good agent tools do not mirror an existing interface but are cut along the workflows an agent actually needs.7 Benjamin Font Pera adds a second axis by sorting the parts by direction of effect: guides act before generation and supply rules, specs and templates, sensors act afterwards and check the result so the agent can correct itself.8 That split transfers straight into a spec, because it forces two questions that otherwise go missing: what the agent knows beforehand, and what its result fails against afterwards.

At the loop layer the stop condition decides. A loop with no reachable target, no budget and no check that ends it is not an autonomous system. It is an unattended cost item.

Context, harness and loop settle what an agent sees, what it may do and how often it does it. Those are three product decisions, not three implementation details.

A critical look

The vocabulary is months old and not settled. codecentric describes openly that its own consultants argued for days about what loop engineering even means.8 Anyone using these terms is better off describing the layer than relying on the label.

The numbers deserve restraint. The OpenAI piece is a vendor describing its own tool rather than a controlled comparison, and the Anthropic posts come from the company whose models run inside them. What holds up best is the Harness-Bench finding, because there different models and harness configurations compete under identical conditions.

The more serious objection comes from Osmani himself. He names three risks: missing verification ("A loop running unattended is also a loop making mistakes unattended"), a slow erosion of understanding, and the comfort of no longer holding an opinion about the output.2 The opposite failure exists as well. A harness can stack checks until nothing autonomous is left. Gartner predicts that more than 40 percent of agentic AI projects will be cancelled by the end of 2027, among other reasons because of escalating costs and unclear business value.9 Where the line between enough and too much sits still has to become clear.

What I changed and what is still missing

My personal knowledge system has run on the lower two layers for months without my having names for them. At the context layer, a guide file at the root and topic specific rule sets loaded only when needed. At the harness layer, reusable commands as tools and a pre-commit hook as a sensor that blocks a commit when a file with credentials slipped in. Every one of those pieces came from a concrete mistake, none from a concept. It covers my own structure such as weekly plans, article drafts and learning goals, never confidential company data.

The weak point sits somewhere I did not expect. The hooks live outside version control. On a new machine the protection is gone, and the knowledge about it survives only in a document someone has to read. A sensor you have to reconnect by hand is not a sensor.

So I am taking on three things. Storing the hooks so they travel with the repository instead of surviving in a manual. Identifying the layer first whenever an AI misbehaves, instead of reaching for the prompt. And writing guides and sensors down separately for every AI feature I specify from now on. Whether that makes specs better or merely longer will show over the coming months.

What stays with you every day

Identify the layer first, then pick the lever

Unreliable on a single task means context. Misses your standards means harness. Needs constant triggering means loop.

Write guides and sensors down separately

What the agent knows beforehand and what its result is checked against are two questions and both belong in the spec.

Every harness component is an assumption

It states what the model cannot do alone. The next model can make it redundant, so review it regularly.

Glossary

Context engineering — curating the information a model sees for a single call.

Harness — everything about an AI agent that is not the model: tools, permissions, state, checks.

Loop engineering — the system that triggers an agent repeatedly, verifies it and keeps it running.

Guides — parts that act before generation: rules, specs, templates, examples.

Sensors — parts that check after generation and feed back so the agent can self-correct.

Agent — a language model that uses tools across several steps and keeps state.

System prompt — the standing instruction before every conversation that sets role and rules.

Context window — the limited amount of text a model can process at once per request.

Token — smallest unit of text processing, roughly a fragment of a word.

Inference — the process of a trained model turning an input into an output.

Attention budget — image for a model's finite capacity to relate pieces of context to each other.

Hook — an automatic intermediate step that enforces fixed rules when an event occurs.

Pre-commit hook — a hook that checks before saving to version control and aborts if needed.

Sandbox — an isolated environment where an agent acts without touching real systems.

MCP — open standard through which agents connect to external tools and data sources.

Skill — a written capability description an agent loads when it needs it.

Sub-agent — a helper agent that takes on a subtask and returns only the result.

Agentic AI — AI systems that carry out steps on their own instead of only answering.

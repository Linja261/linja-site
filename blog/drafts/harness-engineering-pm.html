Nicht das Modell entscheidet. Was Harness Engineering für Produktarbeit heißt.

TL;DR

Die Leistung eines KI-Agenten hängt weniger am Modell als an der Umgebung, in die es eingebaut ist: Werkzeuge, Kontext, Rechte, Prüfungen, Rückkopplung. Diese Umgebung heißt Harness. Sie zu entwerfen ist Produktarbeit, weil dabei festgelegt wird, was ein Agent wissen, tun und nicht tun darf. Für Produktmanagerinnen verschiebt sich die zentrale Frage damit von der Modellwahl zur Umgebungsgestaltung.

In Produktteams wird über Modelle diskutiert, obwohl das Modell selten der Engpass ist. Seit Anfang 2026 hat sich für diese Beobachtung eine Formel durchgesetzt: Agent = Modell + Harness. Das Modell liefert die Schlussfolgerung, das Harness liefert alles andere, also Werkzeuge, Gedächtnis, Ausführungsumgebung, Rechte und die Prüfungen, an denen ein Ergebnis scheitern kann. Der teure Fehler liegt darin, ein misslungenes Agentenergebnis als Prompt-Problem zu behandeln und es einfach noch einmal zu versuchen. Wer so arbeitet, baut ein System, das denselben Fehler beliebig oft wiederholen kann.

Woher der Begriff kommt

Mitchell Hashimoto, Mitgründer von HashiCorp, beschrieb am 5. Februar 2026 seinen Weg durch sechs Stufen der KI-Nutzung.1 Auf Stufe fünf steht eine Gewohnheit, für die er den Namen prägte: „I've grown to calling this 'harness engineering'". Die Regel dahinter passt in eine Zeile: Sobald ein Agent einen Fehler macht, investiert man die Zeit, eine Lösung zu bauen, damit er genau diesen Fehler nie wieder macht. Hashimoto nennt zwei Mittel dafür, nämlich implizite Anweisungen in einer Regeldatei und programmierte Werkzeuge, die eine Prüfung selbsttätig erledigen.

Wenige Wochen später beschrieb Ryan Lopopolo für OpenAI ein Projekt, das nach dieser Logik gebaut wurde.2 Fünf Monate, rund eine Million Zeilen Code, etwa 1.500 gemergte Pull Requests von drei Engineers, ohne von Hand getippten Code. Das sind rechnerisch etwa 3,5 Pull Requests pro Engineer und Tag. Die Menschen in diesem Projekt schrieben nicht den Code, sondern die Umgebung, in der Code entstehen konnte.

Vivek Trivedy hat den Begriff bei LangChain im März 2026 in seine Bestandteile zerlegt.3 Ein Harness besteht demnach aus dem Systemprompt, aus Werkzeugen samt ihren Beschreibungen, aus mitgelieferter Infrastruktur wie Dateisystem, Sandbox und Browser, aus Orchestrierungslogik und aus Hooks, die einzelne Schritte deterministisch erzwingen. Das Dateisystem hält er für das grundlegendste Element von allen, weil nur dort Zustand über eine einzelne Sitzung hinaus überlebt.

Warum das eine Produktfrage ist

Die Bestandteile klingen technisch, die Entscheidungen darin sind es nicht. Anthropics Applied-AI-Team beschreibt Kontext als endliches Aufmerksamkeitsbudget: Jedes Token, das in das Fenster wandert, verbraucht Kapazität und die Genauigkeit sinkt messbar, je voller das Fenster wird.4 Die daraus abgeleitete Regel lautet, die kleinstmögliche Menge hochwertiger Token zu finden. Das ist keine Implementierungsfrage, sondern eine Priorisierungsfrage und Priorisierung unter Knappheit ist der Kern von Produktarbeit.

Dasselbe gilt für Werkzeuge. Ken Aizawa argumentiert, dass gute Agentenwerkzeuge nicht die vorhandene Schnittstelle spiegeln, sondern entlang der Arbeitsabläufe geschnitten werden, die ein Agent tatsächlich braucht: klare Namensräume, sparsame Auswahl, Rückgaben, die nur hochwertige Information enthalten statt technischer Identifikatoren.5 Wer festlegt, welche Arbeitsabläufe ein eigenes Werkzeug bekommen, legt den Funktionsumfang fest. Das ist dieselbe Entscheidung wie bei einer Nutzeroberfläche, nur dass der Nutzer diesmal ein Modell ist.

Ein Harness ist die Entscheidung darüber, was ein Agent wissen, tun und nicht tun darf. Wer sie dem Modell überlässt, hat sie nicht vermieden, sondern nur ungeschrieben getroffen.

Zwei Anwendungen im Produktalltag

Für Produktmanagerinnen folgen daraus zwei getrennte Anwendungen, eine nach außen und eine nach innen.

Die erste betrifft KI-Funktionen im eigenen Produkt. Wenn Leistung an der Paarung aus Modell und Harness hängt statt am Modell allein, dann gehört die Ausführungsumgebung in die Spezifikation und in jedes Anbietergespräch. Harness-Bench hat diesen Effekt gemessen: 106 abgeschlossene Aufgaben, 5.194 Ausführungspfade und erhebliche Unterschiede in Abschlussquote, Prozessqualität, Effizienz und Fehlerverhalten je nach Paarung.6 Die Empfehlung der Autoren ist deutlich: Fähigkeiten sollten nie dem Basismodell zugeschrieben werden, sondern immer der vollständigen Konfiguration. Übersetzt in die eigene Arbeit heißt das, eine Anbieterzusage über ein Modell sagt fast nichts, solange die Umgebung unbekannt bleibt.

Die zweite betrifft die eigene Arbeitsweise. Jede wiederkehrende Korrektur an einer KI ist ein Kandidat für eine dauerhafte Reparatur: eine Regel in der Anweisungsdatei, ein Werkzeug, das die Prüfung übernimmt, oder ein Hook, der einen Fehler blockiert, bevor er entsteht. Der Unterschied zum Prompt-Optimieren liegt darin, dass die Korrektur beim nächsten Mal schon da ist und nicht erneut erinnert werden muss. Werner Heijstek beschreibt dieselbe Struktur aus der Qualitätsperspektive und ordnet die Bausteine in drei Rollen: Regeldateien als Leitplanken, automatische Prüfungen als Sensoren, Menschen an den Stellen, an denen etwas unumkehrbar wird.7

Kritische Einordnung

Die Belege sind jung und teilweise interessengeleitet. Der OpenAI-Bericht ist die Erfahrungsbeschreibung eines Anbieters über sein eigenes Werkzeug und kein kontrollierter Vergleich. Die Seite blockiert zudem automatisierte Abrufe, sodass ich die Zahlen nur über mehrere übereinstimmende Sekundärquellen prüfen konnte. Harness-Bench zeigt, dass Harness-Effekte messbar sind, benennt aber keinen einzelnen Faktor, der sich sauber auf ein anderes Produkt übertragen ließe.

Der ernstere Einwand liegt in der Gegenrichtung. Ein Harness kann Prüfungen so lange stapeln, bis von der Autonomie nichts mehr übrig ist und der Agent teurer wird als die Arbeit, die er abnehmen sollte. Gartner sagt für Ende 2027 voraus, dass über 40 Prozent der agentischen KI-Projekte abgebrochen werden, unter anderem wegen steigender Kosten und unklaren Geschäftsnutzens.8 Zu viel Harness ist eine der Arten, wie diese Kosten entstehen. Wie die Grenze zwischen genug und zu viel verläuft, muss sich erst zeigen.

Was ich verändert habe und was noch fehlt

Mein persönliches Wissenssystem läuft seit Monaten nach dieser Logik, ohne dass ich einen Namen dafür hatte. Eine Regeldatei im Wurzelverzeichnis, thematische Regelwerke, die nur bei Bedarf geladen werden, wiederverwendbare Kommandos für wiederkehrende Abläufe und ein Pre-Commit-Hook, der einen Commit blockiert, wenn versehentlich eine Datei mit Zugangsdaten darin liegt. Jedes dieser Teile ist als Reaktion auf einen konkreten Fehler entstanden, keines aus einem Konzept heraus. Es geht dabei ausschließlich um meine eigene Struktur wie Wochenplan, Artikelentwürfe und Lernziele, nicht um vertrauliche Firmendaten.

Die Bruchstelle sitzt an einer unerwarteten Stelle. Die Hooks liegen außerhalb der Versionierung. Auf einem neuen Rechner ist der Schutz weg und das Wissen darüber steht nur in einer Anleitung, die jemand lesen muss. Ein Sensor, den man von Hand wieder anschließen muss, ist kein Sensor.

Zwei Dinge nehme ich mir deshalb vor. Erstens die Hooks so ablegen, dass sie mitwandern statt in einer Anleitung zu überleben. Zweitens für jede KI-Funktion, die ich künftig spezifiziere, die Ausführungsumgebung genauso schriftlich zu fassen wie die Oberfläche: welche Werkzeuge, welcher Kontext, welche Prüfung vor der Freigabe und welcher Schritt bleibt bewusst beim Menschen. Ob das die Spezifikationen wirklich besser macht oder nur länger, wird sich in den nächsten Monaten zeigen.

Was bleibt für jeden Tag

Derselbe Fehler zweimal ist ein Systemfehler

Beim zweiten Mal nicht das Ergebnis korrigieren, sondern die Umgebung ändern, die den Fehler möglich macht.

Fähigkeit gehört zur Konfiguration, nicht zum Modell

In Spezifikationen und Anbietergesprächen nach der Ausführungsumgebung fragen, nicht nur nach dem Modellnamen.

Kontext ist ein knappes Budget

Was in das Kontextfenster darf, ist eine Priorisierungsentscheidung und gehört deshalb auf den Tisch der Produktseite.

Glossar

Harness — alles an einem KI-Agenten, was nicht das Modell ist: Werkzeuge, Kontext, Zustand, Rechte, Prüfungen.

Agent — ein Sprachmodell, das über mehrere Schritte hinweg Werkzeuge benutzt und dabei Zustand behält.

Systemprompt — die feste Anweisung, die vor jedem Gespräch gilt und Rolle sowie Regeln setzt.

Kontextfenster — die begrenzte Textmenge, die ein Modell pro Anfrage gleichzeitig verarbeiten kann.

Token — kleinste Texteinheit der Verarbeitung, grob ein Wortteil.

Aufmerksamkeitsbudget — Bild für die endliche Kapazität eines Modells, Bezüge im Kontext herzustellen.

Hook — automatischer Zwischenschritt, der bei einem Ereignis feste Regeln erzwingt.

Pre-Commit-Hook — Hook, der vor dem Speichern in die Versionsverwaltung prüft und notfalls abbricht.

Sandbox — abgeschottete Umgebung, in der ein Agent handeln darf, ohne echte Systeme zu berühren.

Orchestrierung — Logik, die Teilaufgaben verteilt, Unteragenten startet und Ergebnisse zusammenführt.

Pull Request — Vorschlag einer Codeänderung, der vor der Übernahme geprüft wird.

Agentische KI — KI-Systeme, die eigenständig Handlungsschritte ausführen statt nur zu antworten.

The model is not what decides. What harness engineering means for product work.

TL;DR

The performance of an AI agent depends less on the model than on the environment it runs in: tools, context, permissions, checks, feedback loops. That environment is called a harness. Designing it is product work, because it settles what an agent may know, may do and may not do. For product managers the central question shifts from picking a model to shaping an environment.

Product teams argue about models even though the model is rarely the bottleneck. Since early 2026 one formula has taken hold for this observation: Agent = Model + Harness. The model supplies the reasoning, the harness supplies everything else, meaning tools, memory, execution environment, permissions and the checks a result has to survive. The expensive mistake is to treat a failed agent run as a prompt problem and simply try again. That approach builds a system capable of repeating the same mistake indefinitely.

Where the term came from

Mitchell Hashimoto, co-founder of HashiCorp, described six stages of his own AI adoption on February 5, 2026.1 Stage five holds the habit he named: "I've grown to calling this 'harness engineering'". The rule behind it fits in one line. As soon as an agent makes a mistake, you spend the time to engineer a fix so it never makes that specific mistake again. He names two instruments, implicit instructions in a guide file and programmed tools that run a check on their own.

Weeks later Ryan Lopopolo described a project at OpenAI built on exactly that logic.2 Five months, roughly a million lines of code, about 1,500 merged pull requests from three engineers, with no code typed by hand. That works out to around 3.5 pull requests per engineer per day. The people on that project did not write the code. They wrote the environment the code could come from.

Vivek Trivedy took the term apart at LangChain in March 2026.3 A harness consists of the system prompt, tools with their descriptions, bundled infrastructure such as filesystem, sandbox and browser, orchestration logic, and hooks that force certain steps to be deterministic. He considers the filesystem the most foundational piece of all, because state only survives beyond a single session there.

Why this is a product question

The components sound technical. The decisions inside them are not. Anthropic's Applied AI team frames context as a finite attention budget: every token entering the window consumes capacity, and accuracy measurably drops as the window fills.4 The rule they derive is to find the smallest possible set of high signal tokens. That is not an implementation question but a prioritisation question, and prioritising under scarcity is the core of product work.

The same holds for tools. Ken Aizawa argues that good agent tools do not mirror an existing interface but are cut along the workflows an agent actually needs: clear namespaces, a sparse selection, returns that carry meaningful information instead of technical identifiers.5 Whoever decides which workflows get their own tool decides the scope of the product. It is the same call as designing a user interface, except this user is a model.

A harness is the decision about what an agent may know, may do and may not do. Leaving it to the model does not avoid the decision. It only leaves it unwritten.

Two uses in everyday product work

Two separate applications follow for product managers, one facing outward and one facing inward.

The first concerns AI features in your own product. If performance depends on the pairing of model and harness rather than the model alone, the execution environment belongs in the spec and in every vendor conversation. Harness-Bench measured that effect: 106 completed tasks, 5,194 execution trajectories, and substantial variation in completion, process quality, efficiency and failure behaviour across pairings.6 The authors are explicit that capability should never be attributed to the base model but always to the full configuration. Translated into daily work, a vendor claim about a model says almost nothing while the environment stays undisclosed.

The second concerns how you work yourself. Every recurring correction you make to an AI is a candidate for a permanent fix: a rule in the guide file, a tool that takes over the check, or a hook that blocks a mistake before it happens. The difference from prompt tuning is that the correction is already in place next time and does not have to be remembered again. Werner Heijstek describes the same structure from a quality angle and sorts the pieces into three roles: guide files as guardrails, automated checks as sensors, humans at the points where something becomes irreversible.7

SIG 2026

A critical look

The evidence is young and partly self-interested. The OpenAI piece is a vendor describing its own tool, not a controlled comparison. The page also blocks automated retrieval, so I could only verify its numbers through several agreeing secondary sources. Harness-Bench shows that harness effects are measurable but names no single factor that transfers cleanly to another product.

The more serious objection runs the other way. A harness can stack checks until nothing autonomous is left and the agent costs more than the work it was meant to absorb. Gartner predicts that more than 40 percent of agentic AI projects will be cancelled by the end of 2027, among other reasons because of escalating costs and unclear business value.8 Too much harness is one of the ways those costs appear. Where the line between enough and too much sits still has to become clear.

What I changed and what is still missing

My personal knowledge system has followed this logic for months without my having a name for it. A guide file at the root, topic specific rule sets loaded only when needed, reusable commands for recurring workflows, and a pre-commit hook that blocks a commit when a file with credentials slipped in. Every one of those pieces came from a concrete mistake, none from a concept. It covers my own structure such as weekly plans, article drafts and learning goals, never confidential company data.

The weak point sits somewhere I did not expect. The hooks live outside version control. On a new machine the protection is gone, and the knowledge about it survives only in a document someone has to read. A sensor you have to reconnect by hand is not a sensor.

So I am taking on two things. First, storing the hooks so they travel with the repository instead of surviving in a manual. Second, writing down the execution environment for every AI feature I specify from now on with the same care as the interface: which tools, which context, which check before release, and which step deliberately stays with a person. Whether that makes specs better or merely longer will show over the coming months.

What stays with you every day

The same mistake twice is a system fault

The second time round, fix the environment that makes the mistake possible instead of the output.

Capability belongs to the configuration, not the model

In specs and vendor conversations, ask about the execution environment and not only about the model name.

Context is a scarce budget

What gets into the context window is a prioritisation call and therefore belongs on the product side of the table.

Glossary

Harness — everything about an AI agent that is not the model: tools, context, state, permissions, checks.

Agent — a language model that uses tools across several steps and keeps state while doing so.

System prompt — the standing instruction that applies before every conversation and sets role and rules.

Context window — the limited amount of text a model can process at once per request.

Token — smallest unit of text processing, roughly a fragment of a word.

Attention budget — image for a model's finite capacity to relate pieces of context to each other.

Hook — an automatic intermediate step that enforces fixed rules when an event occurs.

Pre-commit hook — a hook that checks before saving to version control and aborts if needed.

Sandbox — an isolated environment where an agent can act without touching real systems.

Orchestration — logic that splits work, starts sub-agents and merges their results.

Pull request — a proposed code change that gets reviewed before it is merged.

Agentic AI — AI systems that carry out steps on their own instead of only answering.
